\subsection{Selección de Tecnologías}

\subsubsection{Decisión del Framework Backend: Django vs FastAPI}

Una de las decisiones más importantes fue la elección del framework para el backend. Evaluamos dos opciones principales: Django y FastAPI.

\textbf{¿Por qué Django y no FastAPI?}

Aunque FastAPI es más moderno y rápido, elegimos Django 4.2 por las siguientes razones:

\begin{itemize}
    \item \textbf{ORM robusto}: Django ORM es más maduro y estable para proyectos complejos con múltiples relaciones entre entidades
    \item \textbf{Admin panel integrado}: El panel de administración de Django nos permitió gestionar datos rápidamente durante el desarrollo
    \item \textbf{Seguridad por defecto}: Django incluye protección contra CSRF, XSS, SQL Injection y otros ataques comunes
    \item \textbf{Ecosistema maduro}: Bibliotecas como Django REST Framework, Celery Beat y django-cors-headers están muy bien integradas
    \item \textbf{Documentación extensa}: Django tiene 18 años de desarrollo y una comunidad enorme
    \item \textbf{Escalabilidad empresarial}: Usado por Instagram, Spotify, YouTube - probado en producción a gran escala
    \item \textbf{Experiencia del equipo}: Teníamos más experiencia con Django, lo que redujo la curva de aprendizaje
\end{itemize}

FastAPI hubiera sido ideal para microservicios o APIs de alto rendimiento puro, pero para un sistema integral con autenticación compleja, roles, permisos y múltiples módulos interdependientes, Django fue la mejor opción.

\subsection{Metodología de Desarrollo: Scrum}

Para gestionar el desarrollo del proyecto, utilizamos la metodología ágil \textbf{Scrum} adaptada a nuestro contexto educativo.

\textbf{Configuración del equipo}:
\begin{itemize}
    \item \textbf{Duración total}: 4 meses (aproximadamente 16 semanas)
    \item \textbf{Número de sprints}: 7 sprints
    \item \textbf{Duración de sprints}: 2 semanas por sprint (excepto el último de 2 semanas)
    \item \textbf{Equipo}: 2-3 desarrolladores + 1 instructor como Product Owner
\end{itemize}

\textbf{Distribución de sprints}:

\begin{enumerate}
    \item \textbf{Sprint 1-2}: Configuración inicial, diseño de base de datos, módulo de seguridad básico
    \item \textbf{Sprint 3-4}: Módulo general (instructores, aprendices, fichas, programas)
    \item \textbf{Sprint 5-6}: Módulo de asignaciones (solicitudes, asignación de instructores, estados)
    \item \textbf{Sprint 7}: Refinamiento, corrección de bugs, documentación y despliegue
\end{enumerate}

\textbf{Ceremonias Scrum implementadas}:
\begin{itemize}
    \item \textbf{Sprint Planning}: Planificación al inicio de cada sprint
    \item \textbf{Daily Standups}: Reuniones diarias de 15 minutos (virtuales)
    \item \textbf{Sprint Review}: Demo al instructor/coordinador al final del sprint
    \item \textbf{Sprint Retrospective}: Reflexión sobre qué mejorar
\end{itemize}

\textbf{Herramientas de gestión}:
\begin{itemize}
    \item \textbf{Trello/Jira}: Tablero Kanban para tareas
    \item \textbf{GitHub Issues}: Seguimiento de bugs y features
    \item \textbf{GitHub Projects}: Vista de proyecto integrada con repositorio
\end{itemize}

Esta metodología nos permitió tener entregas incrementales, recibir feedback constante y ajustar prioridades según las necesidades reales del SENA.

\subsection{Patrones de Diseño Aplicados}

\subsubsection{Repository Pattern}

Este patrón nos ayudó a separar la lógica de acceso a datos de la lógica de negocio. En lugar de hacer consultas directamente en los servicios o vistas, creamos repositorios que encapsulan todas las operaciones con la base de datos.

\textbf{Ventajas que obtuvimos}:
\begin{itemize}
    \item Consultas centralizadas y optimizadas
    \item Fácil de testear con mocks
    \item Cambios en la base de datos solo afectan a los repositorios
    \item Código más limpio y legible
\end{itemize}

\subsubsection{DTO Pattern (Data Transfer Object)}

En nuestro caso, usamos \textbf{Serializers de Django REST Framework} como DTOs. Estos nos permiten:
\begin{itemize}
    \item Validar datos de entrada
    \item Transformar modelos a JSON
    \item Controlar qué campos se exponen en la API
    \item Separar la representación de datos de los modelos internos
\end{itemize}

\subsubsection{Service Layer Pattern}

Los servicios encapsulan toda la lógica de negocio. No acceden directamente a los modelos, sino que usan los repositorios.

\textbf{Ventajas}:
\begin{itemize}
    \item Lógica de negocio centralizada
    \item Fácil de testear
    \item Reutilizable en múltiples endpoints
    \item Separación clara de responsabilidades
\end{itemize}

\subsection{Buenas Prácticas Aplicadas}

\subsubsection{Clean Code}

Siguiendo los principios de Martin~\cite{martin2008clean}:
\begin{itemize}
    \item \textbf{Nombres descriptivos}: Variables y funciones con nombres claros
    \item \textbf{Funciones pequeñas}: Cada función hace una sola cosa
    \item \textbf{Comentarios útiles}: Solo donde realmente aportan valor
    \item \textbf{DRY (Don't Repeat Yourself)}: No duplicar código
\end{itemize}

\subsubsection{Principios SOLID}

Aunque suene muy ``pro'', los principios SOLID son super lógicos:
\begin{itemize}
    \item \textbf{S}ingle Responsibility: Cada clase tiene una responsabilidad
    \item \textbf{O}pen/Closed: Abierto para extensión, cerrado para modificación
    \item \textbf{L}iskov Substitution: Las clases hijas pueden sustituir a las padres
    \item \textbf{I}nterface Segregation: Interfaces específicas
    \item \textbf{D}ependency Inversion: Depender de abstracciones
\end{itemize}

\subsubsection{Validaciones}

Validamos los datos en todos los niveles posibles para evitar errores:
\begin{itemize}
    \item \textbf{Frontend}: Validación de formularios con React
    \item \textbf{Serializer}: Validación de tipos y formatos
    \item \textbf{Service}: Validación de reglas de negocio
    \item \textbf{Base de datos}: Constraints y foreign keys
\end{itemize}
